# Domain docs

This is a single-context project. Its domain glossary is `GLOSSARY.md` at the root; architectural decisions live in `docs/adr/` when needed.

## Before exploring

- Read the root glossary and use its vocabulary in specs, issues, tests, and implementation.
- Read existing ADRs relevant to the area being changed.
- If domain documents are absent, proceed silently. Domain-modeling creates them lazily when terms or consequential decisions are resolved.

## Vocabulary and decisions

Use the glossary's canonical terms rather than drifting to synonyms. If a new concept is needed, establish whether it is a real domain gap before recording it.

When a proposal conflicts with an existing ADR, explicitly identify the conflict and the reason to reopen the decision.
